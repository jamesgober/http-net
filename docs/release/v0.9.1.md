# http-net v0.9.1 - Beta

**Date:** 2026-10-29
**Compare:** `v0.9.0...v0.9.1`

**Fixes from the polish pass before 1.0.** Every accepted gap, deferred
item, known issue, and missed target was revisited; the frozen code was
reviewed again by an independent reviewer, fuzzed again, and measured
against every release since 0.6 and against the competitors. The review
found no smuggling, desync, panic, or memory defect, and three smaller
defects, fixed here with regression tests. No API change: `cargo
semver-checks` against 0.9.0 reports none.

## What is http-net?

An HTTP/1.1 engine that does no I/O. Feed it the bytes a socket delivered;
it hands back requests or responses as borrowed views of those bytes,
decodes their bodies, and serializes what you send back. Parsing is strict:
a message two implementations could frame differently is refused with a
specific error, never repaired. Every buffer is bounded by configuration,
and each limit is checked before the bytes it governs are buffered.

## Fixed

- **An error answer to `HEAD` carried content.** When a `HEAD` request
  failed in its body (a bad chunk, the peer closing mid-body), the one
  error response was written as an answer to a `GET`, with the error text
  after the head (RFC 9110 section 9.3.2 forbids content in a response to
  `HEAD`). The blocking adapter's `408` did the same. Both are answers to
  `HEAD` now. The answer always carried `connection: close`, so only a
  front end that ignores it could read the text as a response.
- **Pipelining after a response that closes.** `ClientConn` accepted
  another request after the head of the response being read said the
  connection ends with it (`Connection: close`, HTTP/1.0 without
  keep-alive, a body read until close). RFC 9112 section 9.6 says the
  client stops sending; `can_send` is false now and `send_request`
  refuses with `InvalidState`. The extra request had been counted in
  `outstanding()`, so nothing was misattributed.
- **Body bytes in `Debug` (T-35).** `ServerEvent::Body`,
  `ClientEvent::Body`, `blocking::Incoming`, and the `leftover` of
  `blocking::Upgraded` printed their bytes. A body can carry credentials
  that no field redaction sees, and after a `CONNECT` the leftover can be
  a whole request with its `Authorization` field. They print lengths now,
  like `blocking::Connection` and `ClientResponse`.
- **`blocking::Server::serve` on persistent accept errors** returned
  without waiting for live connections; it now stops them and waits, as a
  shutdown does.

## The polish pass

### Security

An independent review of the frozen 0.9.0 code checked every budget at
its limit and one over, at every two-piece split and byte by byte; every
`Limits` setting at its minimum and maximum; the `u32` offsets and `u64`
totals at their extremes; the connection invariants; client framing of
`HEAD`, 204, 304, 1xx, and `CONNECT`; outgoing injection through every
builder; redaction in every `Debug`; and the bounds of the blocking
adapter. It added five split-invariance properties for paths that had
none (200,000 cases each, all green). Its findings are above; the items
kept as they are, with the reason, are in `docs/SECURITY.md` (review

### Performance

No hot-path code changed. Measured again (`docs/PERFORMANCE.md`, D-72):

- **No regression since 0.6.** Interleaved, nine rounds, pinned:
  `request_head` +0.6% against 0.6.0, +0.0% against 0.7.0, +2.7% against
  0.8.0; the five-field response write -6.7%, -0.1%, -3.2%.
- **The unmet write targets, decomposed.** The response-write benchmarks
  read a one-field request before answering it, which is about 62 ns of
  their time; a prebuilt `Response` adds 1 to 2 ns to that, and
  `write_head` about 12 ns per borrowed field (each field is validated on
  every call). Two ways to cut that measured level and were dropped.
- **Wiping** (`set_wipe(true)`): +5 ns, +2.1%, on the 453-byte browser
  GET, measured for the first time (it was an estimate).
- **Competitors on 0.9.0** (`http-net-bench`): the ratios of 0.6 hold. H1
  head parse 8% behind httparse with SIMD; H3 head at parity; H2 5.4x and
  the H3 client exchange 11.8x faster than hyper; H5 3.0x faster than
  hyper. The run shared the machine with fuzzers, so its absolute times
  are not used; a quiet-machine H1 run comes before 1.0.
- **aarch64:** a manual benchmark workflow (`.github/workflows/bench.yml`)
  on GitHub's Linux arm64 and macOS runners.

### Revisited

The 0.5 wipe idea is measured; the lingering-close byte cap is told apart
from its time cap by a test; the module layout of the 1.0 candidate is
settled (D-71); the buffer bound in `dev/PLAN.md` is corrected. What is
still open is listed in `docs/STABILITY-1.0.md` under "Open before 1.0".

## Testing

371 tests plus 346 doctests, all passing (`cargo test --all-features`):
117 unit tests and 254 integration tests, six more than 0.9.0. New: an error answer to `HEAD` (through
`ServerConn` and through the blocking server, `400` and `408`), no
pipelining after a response that closes, lengths in the `Debug` of the
body events, `Incoming`, and `Upgraded`, and the lingering-close byte
cap.

## Migration from v0.9.0

No code change is needed. Three behaviours can be noticed (an error
answer to `HEAD`, `can_send` after a response that closes, and `Debug`
of body bytes); see `docs/MIGRATION.md`.

## Stability commitment

The API is frozen as the 1.0 candidate: `0.9.x` releases contain fixes
only, and `docs/STABILITY-1.0.md` describes what 1.0 commits to. 1.0.0
ships after the full audit, at the earliest on 2026-11-12, two weeks
after 0.9.0 with no API change in between, on James's decision. The MSRV
is Rust 1.85.
