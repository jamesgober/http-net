# http-net - Plan

> The design of `http-net` and the record of every design decision. Created
> at the start of 0.3 from the library specification (kept privately by the
> maintainer; it stays the contract). This file carries the decision log and
> the defence-ideas log from here on. Read with `dev/DIRECTIVES.md`
> (standards and definition of done), `dev/ROADMAP.md` (versions and exit
> criteria), and `docs/API.md` (the approved public surface).

---

## 1. What it is

`http-net` owns HTTP/1.1 message syntax, framing, and connection state for
servers and clients, and nothing else. It does no I/O: the caller owns
sockets, threads, timers, and the clock, so one core runs under a blocking
loop, `serve-net`'s connection engine, WASP's gateway workers, or a test
that never opens a socket.

It is strict by construction (a message two implementations could frame
differently is refused with a specific `HttpError`, never repaired) and
bounded by configuration, never by input (every budget is checked before
the bytes it governs are buffered).

Not here: TLS (`tls-net`), event loops and accept loops at scale (`net-io`,
`serve-net`), routing (`web-net`), URL normalisation and percent-decoding
(the URL crate), cookies (`cookie-net`), form bodies (`form-net`), generic
field grammar (`parse-net`, from 0.4), content codings (a compression
crate), HTTP/2 (`h2-net`), WebSocket framing (`ws-net`), the full client
(`fetch-net`), proxying (`proxy-net`), caching, authentication.

First consumers: LexerSketch Studio (blocking server and client, upgrade
hand-off), `serve-net` (engine slot), WASP `gateway-io` (parser slot),
`fetch-net`, `proxy-net`, `ws-net`, `h2-net` (shared semantic types).

## 3. Data flow (server side)

```
 socket bytes
   |  feed(&[u8]) or read_buf() + commit(n)     (bounded: Limits::buffer_capacity)
   v
 Buffer [ pinned head | consumed | unread | spare ]
   |  poll()
   v
 HeadScanner.advance   line by line, resumable, budgets checked first
   |  head complete
   v
 interpret_request     start line, target form, version, field facts, framing, Host, Expect, Upgrade
   |                   error -> Failed: one error response allowed, then Closed
   v
 ServerEvent::Request(RequestHead)   views over the pinned head
   |  poll()
   v
 Decoder.step          Length | chunked (size line, data, CRLF, trailers) | none
   v
 ServerEvent::Body(&[u8]) ... ServerEvent::RequestEnd
   |  respond / send_continue / send_body / end_body  -> caller's Vec<u8>
   v
 next request (pipelined bytes already buffered) | AwaitingResponse | Upgraded | Closed
```

The client mirrors it: `send_request` writes into `out`, `poll` reports
`Response`, `Body`, `ResponseEnd`, then `Idle` (reusable) or `Closed`.

## 4. State machines and invariants

Server request state: `Head -> Body -> Complete -> (Head | Closed)`,
`Head|Body -> Failed -> Closed`, `Body|Complete -> Upgraded` (101 or
CONNECT 2xx). Response state is separate (`Idle -> Streaming -> Sent`)
because a response may start before the request body is read.

| Invariant | Test |
|---|---|
| I-S1 after `Failed`, no further request is parsed, whatever bytes follow | `test_connection_is_dead_after_an_error` |
| I-S2 at most one response per request; at most one error response after `Failed` | `test_respond_after_failure_is_once_and_closes` |
| I-S3 a response sent while request body bytes are unread forces `Closed` after it | `test_early_response_closes_connection` |
| I-S4 `Upgraded` only by a 101 answering a complete upgrade request with an offered protocol, or a 2xx answering a complete CONNECT | upgrade tests in `tests/adversarial.rs` |
| I-S5 the parser never waits for input while the buffer is full | asserted by every test driver |

Client: `Idle -> Head -> (Body -> Complete -> Idle|Closed) | Upgraded`;
bytes in `Idle` are `UnexpectedData`; any parse error closes.

## 5. Framing and strictness

RFC 9112 section 6.3 is applied in order, with these stricter choices (each
has a test): CL with TE refused (`ConflictingFraming`), duplicate or list
CL refused even when equal, TE must end in exactly one parameterless
`chunked`, other transfer codings 501, TE in HTTP/1.0 refused, a response
whose TE does not end in `chunked` refused (not read until close), bare LF
and bare CR refused, obs-fold refused (client opt-in replacement in 0.5),
chunk sizes over 16 hex digits refused, a space after a chunk size without
an extension refused. Accepted on purpose: HTTP/1.2 to 1.9 as 1.1, empty
lines before a request line (budgeted), obs-text in values, a status line
without the space after the code (client, from 0.3).

## 6. Memory

- Input buffer: one `Vec<u8>` per connection, grown lazily from 4 KiB by
  doubling, capped at `head + max(head, max_trailer_bytes) + 16 KiB`, where
  `head` is `max_start_line + max_header_bytes` (64 KiB by default). Compaction moves only the pinned head and the
  unread tail, and only when spare space is exhausted: total copying is
  linear in the input.
- Field index: one `Vec` of 16-byte records per connection, reused; at
  most `max_headers` entries.
- Offsets are `u32`, safe because `Limits` caps every budget at 16 MiB.
- Output is caller-owned (`Vec<u8>` today, any `Output` from 0.5).
- Steady state allocates nothing in the core (counting-allocator test,
  `tests/alloc.rs`).

### 0.5 decisions

| Id | Date | Decision | Reason |
|---|---|---|---|
| D-21 | 2026-10-21 | Client pipelining queues only idempotent requests with full bodies, behind a current request that is idempotent with its body sent, and never behind a close, upgrade, `CONNECT`, or expectation. The queue is a fixed array of 32 entries in the connection (about 4 bytes each). | RFC 9112 section 9.3.2; a streamed body behind other requests would tie their responses to it; a fixed array keeps the no-allocation claim. |
| D-22 | 2026-10-21 | When the server closes mid-pipeline, the connection reports `Closed` and `outstanding()` keeps counting the unanswered requests rather than failing them one by one. | The caller decides whether to retry (they are idempotent by D-21); one number is enough to do it. |
| D-23 | 2026-10-21 | `reset()` keeps the limits and the trailer-reporting and wipe settings, and resets per-connection state including `set_keep_alive` (allowed again) and `requests_served`. | Settings describe how the driver uses the object; keep-alive control and the count describe one peer. |
| D-24 | 2026-10-21 | Wiping is done by the buffer: the finished request's region at each exchange, the vacated tail on every compaction, everything on reset, release, and drop; each `fill(0)` is followed by `core::hint::black_box` so it is not removed. Only `ServerConn` has `set_wipe` (the spec's A-46); the client's buffer supports it internally for later. | Compaction leaves stale copies past the new end that a per-request wipe alone would miss (the wipe test checks it with a control run). |
| D-25 | 2026-10-21 | `Request::forward_from` copies the target as received (absolute form stays absolute) and every end-to-end field in order, drops the hop-by-hop set of RFC 9110 section 7.6.1 plus every name `Connection` lists, and does not copy `content-length`: the body mode (chunked or a length) is taken from the head's framing and the connection writes the framing field. An upgrade request is refused with `InvalidState`. | Re-serializing is the proxy-net rule; the framing field is the connection's, and copying it would also trip `ReservedHeader`. An upgrade cannot be forwarded as a request (its fields are hop-by-hop); a proxy tunnels it. |
| D-26 | 2026-10-21 | `is_hop_by_hop` treats `trailer` as hop-by-hop with the RFC's list. | It announces the trailers of a body that each hop re-frames; the spec lists it (A-230). |
| D-27 | 2026-10-21 | The HTTP/2 preface is checked only before a connection's first request. While the buffered bytes are a proper prefix of the preface the connection reports `NeedInput` instead of parsing (at most 23 bytes); at EOF it parses them normally. | The first 18 bytes of the preface are a complete HTTP/1.1-shaped head, so deciding earlier would make the result depend on how the bytes arrived (an `UnsupportedVersion` for one split, `Http2Preface` for another). | D-28 | 2026-10-21 | Client obs-fold leniency rewrites in place in the connection buffer: a line end inside the field section is held back from the head scanner until its next byte arrives; a following SP or HTAB turns the CR LF into SP SP and the line continues. Trailers are not unfolded. | RFC 9112 section 5.2 asks a user agent to replace each fold with one or more SP; holding back one byte keeps the result independent of how input is split, with no copy and no allocation (OD-7). Trailers are rare and have no user-agent rule of their own. |
| D-29 | 2026-10-21 | The head scanner is generic over a crate-private field sink: the connections push into their `Vec`, discarded trailers into nothing, the stateless parsers into the caller's array (a full array is `TooManyHeaders`). | D-30 | 2026-10-21 | `RawHead::bytes()` starts at the first byte the connection kept for the head, so empty lines a client sent before the request line (RFC 9112 section 2.2) stay in it and `start_line()` begins after them. | D-31 | 2026-10-21 | `from_parts` checks the structure (every span inside the bytes, method, target, and version where the facts say, field lines back to back with token names and clean trimmed values, the blank line last, the host span equal to a `Host` field) but takes the framing facts (body length, keep-alive, upgrade) as given. | Recomputing them is the parse the passport exists to avoid; the facts travel with the same copy as the bytes. | D-32 | 2026-10-21 | `OwnedRequestHead::into_parts` added beside `view` and `from_parts`. | `from_parts` takes the vectors by value; without a way back, a passport pool would lose its grown buffers on every request and allocate again. |

| D-42 | 2026-10-21 | `ChunkedDecoder` runs the connection's `body::Decoder` in a third trailer mode, `Locate`, that validates the trailer section and reports its length without storing fields. | D-43 | 2026-10-21 | `impl<O: Output + ?Sized> Output for &mut O`. | A sink can be passed down by reference without being moved, the same pattern as `std::io::Write`. |
| D-44 | 2026-10-21 | Two hot calls are `#[inline(always)]`: `parse_field` (the scanner is now compiled once per field sink, D-29) and `start_response` (shared by `respond`, `respond_into`, and `write_head`, D-37). `start_response` is generic over a crate-private `HeadSource` trait implemented by `Response` and `ResponseHeadRef`, instead of taking a runtime `HeadSpec` enum. | The interleaved A/B against 0.4.0 measured +8% on the head benchmark, +12% on client response parsing, and +7% on response writing after the merges; with these changes all three are back within run-to-run noise of 0.4.0. One code path remains, compiled per source. |
